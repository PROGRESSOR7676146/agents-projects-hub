# Сообщения и файлы между агентами: варианты решения

Проверено 20 октября 2026 года. Это предложение для выбора, реализация не включена.
Исходная основа Hub: `afdf85fcf3a3ee4085d7868cecf688062babf6ff`.

Рекомендую общий журнал сообщений и проверенных вложений внутри Hub. Для
сообщений независимых ботов стоит использовать новый поддержанный Telegram
Bot-to-Bot Communication Mode, если его доступность подтвердится на наших
ботах. Постоянный пользовательский Telegram-аккаунт для чтения групп пока
не нужен. Получение контекста и запуск ответа должны управляться отдельно.

## Что изменилось в Telegram

Прежний тезис роудмепа «боты никогда не видят сообщения других ботов» устарел.
В официальном changelog Bot API 10.0 от 8 мая 2026 описана ограниченная
видимость чужих bot-сообщений. Актуальное руководство уточняет:

- В группе бот может адресовать другого командой `/command@example_review_bot` или
  ответом на его сообщение. Достаточно включённого Bot-to-Bot Communication
  Mode хотя бы у одного из двух ботов.
- Получатель с этим режимом видит все сообщения других ботов в группе,
  если у него есть права администратора либо отключён Group Privacy Mode.
- Для переписки двух ботов в личных сообщениях режим нужен обоим.

При этом официальный FAQ всё ещё содержит старое абсолютное ограничение.
Для выбора реализации опираемся на более новые changelog и руководство, а
для подтверждения конкретной установки понадобится отдельная live-проверка.
Настройки ботов и групп в ходе исследования не менялись.

Новый режим Telegram сам по себе не включает обмен в Hub: текущие
`parse_topic_message` и `parse_direct_message` отбрасывают вход от ботов.
Нельзя просто убрать эту проверку и пропустить бота как владельца. Нужен
отдельный путь приёма недоверенного содержимого, без доступа к командам и approvals.

Для пассивной видимости обычных ответов режим нужен каждому принимающему боту.
Оба варианта — admin-права и отключённый Privacy Mode — открывают боту весь
человеческий трафик группы. Вариант admin дополнительно даёт назначенные права
управления: следует отдельно согласовать минимальный набор. Ни один из этих
вариантов не включается автоматически. Выбор должен учитывать,
какие данные группа готова раскрыть каждому участнику. Если это неприемлемо,
следует выбрать ограниченный журнал Hub или проверенный мост Gateway.

## Сравнение вариантов

| Вариант | Что даёт | Ограничение и стоимость | Оценка |
| --- | --- | --- | --- |
| Журнал и вложения Hub | Единый контекст для его провайдеров, происхождение, дедупликация и восстановление | Нужны связи сообщения с вложениями и ограниченная выдача; нынешний журнал хранит сокращённый текст | Основа решения |
| Новый bot-to-bot режим Telegram | Видимость сообщений независимых ботов, в том числе вне общего процесса Hub | Оба способа дают весь человеческий трафик; admin ещё и назначенные права управления; режим каждому получателю, отдельный приём и live-проверка файлов | Дополнение к журналу |
| Мост с Hermes Gateway | Прямой обмен видимыми событиями при независимом runtime Hermes | Требует поддержанных входов/выходов Gateway, общей идентичности событий и отдельной проверки файлов | Резервный вариант при ограничении Telegram |
| Наблюдатель через Telegram user-сессию | Получение сообщений как обычным участником группы | Постоянная авторизация аккаунта, дополнительные права, хранение сессии, восстановление и ещё один путь доставки | Только если более простые варианты не покроют нужные случаи |
| Прямая передача в native-сессии провайдеров | Возможность доставлять контекст во время работы, где runtime это поддерживает | Разные семантики, конкуренция с активным turn, больше recovery и проверок полномочий | Отдельный последующий этап |

Транспортные варианты не заменяют надёжное хранение и проверку доступа.
Одна доставка Bot API не доказывает, что модель получила или прочитала файл.

## Предлагаемый первый объём

1. Включать общий контекст только для явно разрешённых числовых пар
   `(chat_id, message_thread_id)` и участников, зарегистрированных по числовому
   bot user ID (`from.id`). Username — отображение, не основание доверия. Вначале —
   одна тема одного проекта; без переноса содержимого между проектами.
2. Хранить сообщения с автором, адресатом, исходным message ID, версией правки
   и статусом происхождения. Локально сформированный ответ и подтверждённая
   отправка в Telegram должны различаться. Неопределённая отправка остаётся
   неопределённой; её нельзя повторять ради появления записи в общем контексте.
3. К каждому вложению прикреплять проверенные байты или явную причину
   недоступности, размер, имя и SHA-256. Telegram `file_id` привязан к боту;
   передавать этот ID другому боту вместо содержимого нельзя.
   При получении документа через Telegram каждый бот использует свой `file_id`
   из своего входящего update для `getFile`; лишняя пересылка не обязательна.
4. Для первого этапа — текст сообщений и UTF-8 документы, включая Markdown.
   Повторно использовать действующие пределы входящих материалов: до 20 MiB
   на файл, 10 материалов и 80 MiB на задание, до 120 000 символов текстовой
   вставки. Это верхние пределы, а не обещание загрузить всё в контекст модели.
   Для облачного `getFile` действует собственный предел Telegram 20 MB;
   более строгий фактический предел транспорта имеет приоритет.
5. PDF, архивы, изображения, аудио и видео не объявлять прочитанными через
   текстовый путь. Нужна отдельная подтверждённая поддержка конкретного
   адаптера; иначе получатель видит тип материала и причину недоступности.
6. Доставлять ограниченный пакет при следующем обычном обращении к агенту в
   этой теме. Само появление сообщения коллеги модель не запускает. В уже
   выполняющийся turn принудительную вставку в первом этапе не включать.
   Это требует утверждённого изменения нынешнего REQ-CTX-002: сейчас чужая
   история выдаётся только по явному `/context`.
   Также нужен новый ADR, явно определяющий совместимость с REQ-COLLAB-002:
   его запрет bot-to-bot review-канала нельзя обходить названием «контекст».
   Предложение не возвращает роли ведущего/советника, автоматическое назначение
   ревью или handoff. Изменение этой границы отдельно входит в решение владельца.
7. Файлы выдавать через подготовленный пакет конкретного разрешённого проекта,
   без предоставления модели Hub state, ключей или служебных endpoint.
   Содержимое остаётся недоверенными данными; имя файла не становится путём
   или командой. Существующие отдельные ограничения Claude сохраняются.
8. Предлагаемый срок хранения новых копий вложений — 30 дней с явным
   обозначением истечения. Удаление байтов не должно превращать старую
   запись в успешную доставку или уничтожать доказательство неизвестного исхода.
   Срок и правила удаления нужно утвердить вместе с дизайном.

Защита от бесконечного обмена нужна и без моделей: bot-вход не должен вызывать
никакой автоматический Telegram-ответ, включая ошибку, подтверждение и сообщение
о недоступном файле. Причины фиксируются пассивно и доступны владельцу по его
запросу. Предлагаемые начальные пределы — 30 событий и 40 MiB вложений в минуту
на отправителя в теме, 500 MiB сохранённых вложений на тему. Переполнение
ограничивает приём и учитывается в счётчике пропусков; не порождает ответ боту.
Это параметры предлагаемого дизайна, а не действующие настройки.

Для автоматической вставки предлагается отдельный предел **2 000 входных
токенов и 8 сообщений на обычный turn**, с контролем до отправки провайдеру.
Если точный подсчёт конкретного провайдера недоступен, автоматическую вставку
следует отключить и оставить явный запрос. Вложения целиком в этот бюджет не
втискиваются: показывается наличие проверенного материала, а его доступность
через поддержанный ограниченный файловый путь подтверждается отдельно. Файл
не считается прочитанным по одному наличию. Расширение по явному запросу
пользователя использует обычные лимиты материалов и видимое предупреждение
о дополнительном контексте. Нужны выключатель для темы и отказ на отдельный
turn. При 100 обращениях добавка ограничена 200 000 входных токенов; отдельного
вызова модели нет. Денежная цена зависит от выбранного провайдера и маршрута,
а при подписке расходуется её контекст/квота; бесплатность не предполагается.

REQ-CTX-005 остаётся обязательным: скрытые рассуждения, raw tool/terminal output,
credentials, приватные приглашения и environment dumps в общий пакет не входят.
Доверенные адаптеры экспортируют только разрешённые типы видимых событий.
Произвольный поток независимого бота нельзя считать безопасным после одной
регулярной проверки текста: его включение требует проверенного экспортного
контракта, иначе содержимое не попадает в модельный пакет, а недоступность
обозначается явно. Каждый выданный пакет, включая автоматический, получает
атрибуцию и маркировку недоверенного контекста по REQ-CTX-006.

Такой первый этап даёт взаимную видимость при следующем обращении, но не
автоматический диалог агентов и не немедленное изменение уже активного turn.
Если нужен самостоятельный обмен репликами, это отдельное решение о запуске,
числе ходов, бюджете и остановке. Оно не следует из разрешения читать сообщения.

## Восстановление и приёмка

После рестарта одно исходное сообщение не должно повторно попадать в пакет.
Нужны устойчивые идентификаторы событий и отдельный курсор каждого получателя.
Два приёмника — локальный журнал и Telegram — должны узнавать одно событие,
а не создавать два экземпляра. Если точную связь установить нельзя, система
должна показать неопределённость, а не угадывать по совпадению текста.

Перед внедрением проверить в обе стороны:

- Два агента видят текст и одинаковый SHA-256 реального UTF-8 вложения.
- Доступ к соседней теме и другому проекту закрыт; неподтверждённый бот
  не получает командных или approval-полномочий.
- Вложение с вредоносными инструкциями остаётся контекстом; имя с `../`,
  подмена байтов, превышение лимита и недоступный тип отклоняются явно.
- Правка сообщения создаёт понятную новую версию; повтор Telegram update,
  рестарт и сбой после сохранения не дают повторной обработки или ответа.
- Два бота, отвечающие немедленно, не создают цикл и не вызывают модель
  без отдельного разрешённого запуска; ошибки обработки тоже не отвечают боту.
- Поток одного отправителя ограничен по частоте и хранению, отказ от вставки
  на turn/тему работает, пакет не превышает 2 000 токенов; переполнение видно.
- Приходят ли `edited_message` и точный `message_thread_id` для сообщений
  ботов, подтверждено в выделенной теме; отсутствие событий не скрывается.
- Переполнение пакета и истечение хранения видны получателю. Claude не
  получает новые инструменты или изображения через побочное включение обмена.

Нынешний `/context` полезен как контрольный сценарий, но недостаточен для
цели: `record_visible_turn` сохраняет сокращения пользовательского текста и
ответа, а `visible_context_snapshot` не выдаёт содержимое приложенных файлов.

## Что требуется выбрать перед реализацией

Рекомендуемый вариант: **журнал Hub плюс bot-to-bot приём, чтение на следующем
обычном ходе, без автоматических ответов, первый этап — текст и UTF-8 файлы**.
Это предложение, а не уже утверждённое изменение поведения. Альтернатива —
сразу включить самостоятельный диалог; тогда до разработки нужно определить
его бюджеты и правила остановки.

Предварительная оценка рекомендуемого первого этапа — **6–12 рабочих дней
одного исполнителя**: 3–5 на журнал и выдачу проверенных файлов, 1–3 на
отдельный приём bot-событий, 2–4 на проверки, review и приёмку. Это инженерная
оценка объёма, не измеренный срок и не обещание даты; ожидание решений владельца
не включено. Короткая проверка Telegram может изменить диапазон. Мост Gateway
добавляет проверку совместимости и файловых lifecycle; постоянная user-сессия —
ещё и отдельную эксплуатацию авторизации. Native-вставка в активные turns
требует работ по каждому провайдеру и в эту оценку не входит. Расход токенов
ограничен предложенным бюджетом выше; хранение ограничено отдельно.
