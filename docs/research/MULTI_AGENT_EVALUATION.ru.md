# Проверка гипотезы командной работы агентов

Дата: 2026-09-27. Статус: приложение к исследованию, не принятый план внедрения.
Исходная ревизия Hub: `ea5af70b9332d8463b83d19f95ccda7c09e71faf`.

[Основное исследование](MULTI_AGENT_COLLABORATION.ru.md) описывает архитектуру,
ограничения и первичные источники. Здесь собраны варианты развития и предлагаемые
эксперименты; их результаты пока не получены.

Скоринг участников и распределение ресурсов теперь выделены в
[принятое продуктовое направление](../product/EVALUATION_AND_ALLOCATION.md).
Методы измерения, сравнения и применимость Jev исследованы
[отдельно](AGENT_SCORING_AND_ALLOCATION.ru.md); остальная архитектура командной
работы здесь по-прежнему является предложением.

## Варианты развития и рекомендуемая последовательность

| Вариант | Польза | Ограничения | Оценка |
| --- | --- | --- | --- |
| Только чат и инструкции «не мешайте друг другу» | Быстрый демонстрационный UX | Нет enforcement, устойчивых задач и точной приёмки | Недостаточно для writable team |
| Ведущий пишет, остальные консультируют | Независимые review и альтернативы с меньшим риском | Не ускоряет независимую реализацию напрямую | Хороший первый эксперимент |
| Локальный coordinator + MCP + изолированные lanes | Сохраняет Hub adapters и контроль, поддерживает общую работу | Требует предметной модели tasks и изменения topic/FIFO границы | Рекомендуемая основа |
| A2A между всеми участниками сразу | Стандартные endpoints и внешний interoperability | Дополнительные серверы, auth и версии без решения Git-конфликтов | Отложить до внешнего агента |
| Полная замена на agent framework | Готовые primitives диалога и orchestration | Необходимо заново доказать Hub approvals, recovery и root isolation | Исследовать только при конкретном дефиците существующего ядра |

Предлагаемые этапы являются материалом для решения владельца, не принятым roadmap.

1. **Контракт команды и офлайн-модель.** Уточнить границу conversation/task/lane,
   роли, budget admission, stop и leader epoch. Проверить state machine на fake
   adapters до продуктивных вызовов. Отдельно рассмотреть архитектурные hotspots,
   как требует [maintenance policy](../product/MAINTENANCE.md).
2. **Один ведущий и вызванный reviewer.** Общий видимый чат, roster, отдельная
   read-only сессия/снимок, типизированный task/result, адресный inbox, явная
   приёмка. Нулевые вызовы не приглашённых моделей. Автоматические обсуждения
   пока ограничены конкретным review workflow.
3. **Два исполнителя в разных lanes.** Отдельные ветки, ресурсы тестов, bounded
   concurrency, dependency graph, integration queue и проверка общего candidate.
   Ведущий может работать над своей независимой частью одновременно.
4. **Помощники и события.** Ограниченные дочерние задачи, учёт всего дерева,
   разрешённые подписки, короткие раунды критики и возобновление на событиях.
5. **Внешний A2A adapter.** Только когда появляется конкретный remote agent,
   которого полезнее подключить как самостоятельный сервис. Проверить auth,
   deduplication, cancellation и status mapping на точных версиях.

При переходе к реализации изменения затронут владельцев контрактов:
`REQ-ROUTE-006`, `REQ-CTX-002/004/007` — пробуждение и обмен;
`REQ-ID-005/007` — изоляция и participant sessions;
`REQ-QUEUE-002/003/004` — task lanes, capacity и uncertainty;
`REQ-WRITER-001` — сохраняемая единственность writer на scope;
`REQ-SEC-002/006` — происхождение полномочий и делегация.
Универсальный provider-neutral Session Bridge и новые провайдеры не нужны для
первого этапа. Автономный ведущий с видимой provider identity также не требует
скрывать все runtime за одним безымянным «суперагентом».

## Критические границы прототипа

**Одна тема и несколько lanes.** Это изменение нынешней связи темы с одним
execution scope, а не настройка существующего scheduler. Новый task stream
получает собственную identity и scope, при этом сохраняет видимую связь с
исходным numeric topic. Нужны reviewed ADR и additive migration; старые jobs,
origins, local leases и callbacks не должны начать ссылаться на другую lane.
Reply адресует конкретного автора/участника, но сам не разрешает параллельную
запись. Нынешние satellite sessions не следует называть готовыми team workers.

**Контекст и ADR 0009.** Для явно разрешённого workflow потребуется уточнить
ADR 0009 и owning requirements. Не следует снимать trigger, запрещающий
`pending_handoffs`, и возвращать прежнюю инъекцию чужой истории при переключении
модели. Типизированные task messages и разрешённые context snapshots получают
отдельный reviewed путь с происхождением и бюджетом. Обычный режим сохраняет
нынешний запрет; тесты доказывают обе ветви. Простое событие `artifact_submitted`
не даёт разрешения на inference вне этой policy.

**Делегирование при одном слоте.** Родитель сначала сохраняет поручение и
continuation, затем действительно завершает свой turn. Worker подтверждает,
что принадлежащие ему пишущие команды завершены и root можно освободить.
Только после этого помощник занимает доступный слот в собственной lane;
позднее родитель продолжает новым разрешённым turn. Сохранение checkpoint само
по себе не доказывает остановку. Если runtime не даёт доказать эту границу,
параллельное/синхронное делегирование в такой конфигурации отклоняется или
переносится до подтверждённой терминальности. Read-only helper тоже потребляет
модельную capacity: имя роли не является обходом scheduler.

**Остановка потомков.** Для локальной writable-роли требуется контролируемое
владение процессами: supervisor с границей процесса/группы/cgroup, запрещающей
потомку незаметно покинуть её. Один process-group kill недостаточен, если runtime
может создавать detached процессы. Systemd-managed компоненты останавливаются
через service manager. Для remote runtime необходимо подтверждение остановки
либо сохранение `indeterminate` и карантина его результатов/ресурсов. Ответ
cancel API не доказывает прекращения внешних эффектов. При отсутствии этих
возможностей native вложенная writable-делегация выключается; используются
Hub-managed tasks с отдельными lanes. Пользовательский team-stop закрывает
admission новых потомков атомарно со сменой поколения, затем останавливает уже
известных; поздние регистрации и результаты старого поколения не принимаются.

Новую ответственность координации следует вынести за существующие крупные

провайдера или таблицам. Конкретное выделение модулей определяется архитектурным
review перед реализацией.

## Как доказать пользу и безопасность

Для сравнения нужны повторяемые фикционные задачи четырёх типов: независимые
изменения модулей, тесно связанные изменения API, поиск ошибки с несколькими
гипотезами, ревью кода/документации. Сравнить одного сильного агента, ведущего с
помощниками и ведущего с коллегой другого провайдера. Использовать одинаковые
базовые ревизии и критерии, фиксировать различия разрешённых затрат. Нужны
несколько прогонов; один удачный показ не подтверждает общее превосходство.

Измерять время до принятого интегрированного результата, общие observable usage
и затраты, число дефектов, rework, конфликтов, обращений к владельцу, потерь
контекста и повторных вызовов. Отдельно учитывать cache и неизвестные расходы.
Практический порог выгоды владелец выбирает до live эксперимента; численного
обещания экономии это исследование не даёт.

Минимальная офлайн-приёмка будущего механизма:

- не приглашённый агент получает ноль productive calls; обычный режим сохраняет
  текущую семантику Reply, mention, `/context` и смены модели;
- два конкурентных claim дают одного владельца; один root не получает двух
  writers, а разные разрешённые lanes действительно прогрессируют параллельно;
- попытки записи в чужую lane, подделки отправителя/роли и relay approvals
  отклоняются на технической границе;
- повтор события не порождает повторного вызова; crash после invocation
  сохраняет неопределённость; crash после результата повторяет только доставку;
- parent/child на одном provider при capacity=1 не образуют deadlock;
- stop охватывает выбранную задачу и предусмотренных policy потомков, сохраняет
  неизвестные исходы и не затрагивает независимую команду;
- изменённый candidate/target HEAD делает прежние проверки неактуальными;
  тесты выполняются на точной итоговой ревизии;
- смена ведущего отклоняет действия старого поколения; отсутствие процесса
  само по себе не разрешает повтор потенциально выполненной работы;
- лимиты учитывают коллег и помощников вместе; сообщения и мониторинг не
  запускают скрытые платные циклы;
- restart восстанавливает назначения, inbox, artifacts, budgets и pending
  decisions без передачи hidden reasoning, credentials или полного transcript.

Поверх этих проверок требуется отдельно разрешённый provider/Telegram E2E с
двумя runtime на одной точной чистой ревизии и подтверждённой идентичностью всех
обязательных компонентов. Сейчас доказан только результат исследования; новая
командная работа не объявляется реализованной или принятой в deployment.
