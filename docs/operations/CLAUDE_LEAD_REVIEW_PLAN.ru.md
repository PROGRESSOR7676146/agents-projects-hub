# Claude Code и Codex: ведущий и советник

Дата: 2026-09-27. Статус: принят ограниченный объём этапов 0–2;
начат ограниченный Claude worker scaffold, полная реализация и live-приёмка
ещё не выполнены.
Владелец продуктового решения: владелец репозитория.
Владелец реализации: сопровождающий Hub.
Исходная исследовательская ревизия:
`ea5af70b9332d8463b83d19f95ccda7c09e71faf` — исходное чтение кода.
Последняя проверенная репозиторная основа:
`3750ccfb0f8eb98333f9219f3a697d6328890d04` — текстовый Claude worker,
нативная UUID/root-привязка, ограниченный поток и восстановление сохранённого
результата; canonical и независимые проверки пройдены. Это не deployment
или live acceptance. Следующий шаг: проверяемая граница human approvals,
затем инструменты ведущего и техническая изоляция советника.

Этот план сужает ближайшее внедрение относительно
[исследования командной работы](../research/MULTI_AGENT_COLLABORATION.ru.md).
Параллельные пишущие агенты, обучаемый выбор исполнителя и полная командная
платформа отложены до измеренной потребности. Принятые границы первого выпуска
закреплены в [продуктовых модулях](../product/PRODUCT_REQUIREMENTS.md) и
[ADR 0040](../decisions/0040-bounded-claude-codex-lead-advisor.md); этот план
фиксирует порядок работ. Нынешние routing/context/approval правила остаются
в силе до реализации и приёмки режима сотрудничества.

## Принятый продуктовый объём

Цель — нативный Claude Code через локальный CPA с подписочным аккаунтом и существующий Codex в одном
проектном чате. Владелец выбирает старшие модели, effort и ведущего вручную.
Оба могут участвовать в планировании; любой может стать ведущим после безопасной
передачи роли. Переноса нативного контекста между компаниями не предполагается.

- Роли задаются для темы: один ведущий с правом менять файлы. Между всеми
  темами сохраняется один активный writer на canonical root проекта. Второй может
  читать разрешённые материалы, критиковать план, предлагать альтернативы и
  проверять результат, но не менять проект, запускать пишущие команды или
  создавать пишущих помощников. Ответ в чате не является файловой записью.
- Советник вызывается пользователем либо ведущим внутри явно включённого
  ограниченного workflow. Само присутствие в теме не запускает модель.
- Начальная реализация советника обходится без его собственных субагентов.
  Для помощников ведущего предлагается один уровень делегации поиска и анализа
  с правами только на чтение. Пишущая делегация не входит в первый выпуск;
  изменения выполняет ведущий. Это сохраняет границу одного writer.
- Разрешённые запросы, переданные материалы, выводы и итоговое решение видны
  владельцу. Результат ведущего содержит принятые замечания и основания
  отклонения существенных замечаний; обязательного консенсуса нет.
- Подписка Claude Code — выбранный путь. Не включать API-биллинг, платный
  fallback, extra usage или покупку ресурсов как неявное продолжение.
- Автоматическое ранжирование, Jev, модель-судья и дублирующие эксперименты
  отложены. Выбор ведущего опирается на суждение человека.

Это отдельный режим сотрудничества. Обычный адресный чат сохраняет свои
правила; явное включение режима не означает передачу всей истории всем моделям.

## Предел усложнения первого выпуска

Использовать существующие Controller, provider worker, SQLite queue/outbox и
механизмы изоляции Hub. Отдельный Claude worker в существующей модели допустим;
новый управляющий сервис, отдельная БД, брокер событий, универсальный agent
framework или ML-сервис в этот выпуск не входят. Небольшой локальный интерфейс
поручений допустим, если он использует те же admission и ownership границы.

Предел продукта — один ведущий, один советник, ручной выбор ролей и минимальный
журнал. Если выяснится, что для этого необходима существенно более сложная
инфраструктура, сначала пересмотреть подход и объём. Не расширять архитектуру
автоматически ради выполнения предварительной оценки сроков.

## Технический путь и открытые проверки

В исходной исследовательской ревизии не было нативного runtime Claude. Названия
Claude в каталоге другого runtime не дают Claude Code sessions, approvals или подписочную
интеграцию. Повторно используем имеющиеся queue/outbox, root validation,
writer ownership и ограниченные callback/catalog механизмы.

Первый кандидат — официальный локальный Claude Code CLI с `-p`, структурированным
потоком и точным `--resume`. Управление только через поддерживаемые интерфейсы;
никакого screen scraping или воспроизведения приватного сетевого протокола.
Наблюдаемое поведение проверяется на закреплённой версии CLI. Первый
репозиторный адаптер использует ограниченный текстовый режим и три независимых
слота. Он намеренно не выдаёт себя за пишущего ведущего или читающего код
советника: для них ещё нужны human approval host, системная граница чтения,
точный local/return и live-проверка маршрута CPA без платного fallback.

CPA маршрутизирует запросы модели, но не выдаёт разрешения инструментам.
Нынешний Claude worker отключает hooks, tools и permission prompts. У
проверенного tlive режим approval-only для Hub-сессии реализован на пути
Codex app-server; наличие Claude `PermissionRequest` hooks само по себе не
доказывает безопасную работу фонового `claude -p` и не выключает второй
reply-to-continue канал. Пакет A должен доказать изолированную конфигурацию
hooks/approval host и отказ без разрешения при сбое до включения инструментов.

### Следующая граница разрешений

Прямое подключение существующего tlive Claude hook пока не проходит контракт:
ответ `allow` не отличает новое решение человека от trust/per-tool/auto-approve
политики, а `defer` и пустой ответ возвращают управление нативному потоку вместо
явного отказа. Кроме PermissionRequest, общий plugin устанавливает Stop с
reply-to-continue. Режим approval-only для Codex не является изоляцией Claude.
Нужно отдельное подтверждение human-only решения, привязки конкретного запроса
и отсутствия второго conversation writer; глобальную настройку tlive не менять.

Основной runtime остаётся официальным Claude CLI в очереди Hub. Следующий
кандидат — нативный permission host через поддерживаемый интерфейс CLI;
`PermissionRequest` hook и `--permission-prompt-tool` проверяются как разные
механизмы. Hook не содержит `tool_use_id`, поэтому session/root/tool-name сами
по себе не являются точной identity запроса. Пустой ответ, изменённый input,
permission updates, смена поколения, timeout, restart и потеря канала не должны
становиться новым разрешением. До доказательства этой границы инструменты
остаются отключены. Не добавлять неиспользуемый универсальный approval broker.

Первый защитный шаг — пассивная проверка объявленных возможностей CLI и отказ
при наблюдаемом нарушении текстовой политики. Она не проверяет подписку,
upstream CPA, реальное поведение permissions или готовность human host и не
вызывает модель. После неё требуется реальный bounded human round trip,
техническая граница советника и отдельно разрешённая native/Telegram приёмка.

По официальной документации, прочитанной 2026-09-27:

- CLI поддерживает подписочный вход и программный запуск. Однако наличие
  `ANTHROPIC_API_KEY` в non-interactive окружении переключает доступ на ключ;
  есть и другие источники с более высоким приоритетом. Проверка происхождения
  авторизации нужна до продуктивного вызова, без вывода или копирования секретов.
- Режим `--bare` не использует подписочную OAuth-авторизацию. Нельзя выбрать его
  как готовое решение изоляции для этого пути. `--safe-mode` сохраняет обычную
  авторизацию, но не отменяет policy-configured hooks; текстовый worker дополнительно
  задаёт `disableAllHooks` через явные settings. Это не доказательство отсутствия
  всех управляемых автоматизаций: противоречащая политика остаётся причиной отказа,
  а наблюдаемый hook или tool event после запуска сохраняет неопределённость.
- `--tools` ограничивает встроенные инструменты, но не MCP. `--allowedTools`
  означает разрешение без запроса, а не исчерпывающий список доступных tools.
  Plan mode сам по себе не устанавливает требуемую границу советника.
- Agent SDK отдельно ограничивает предоставление claude.ai login/лимитов
  сторонними продуктами без согласования. Нельзя считать подписку автоматически
  подходящим способом авторизации SDK. Пакет A проверяет поддерживаемую границу
  локального управления уже авторизованным пользовательским CLI и её отличие
  от предлагаемой продуктом авторизации; при неясности граница остаётся открытой.
  Смена обёртки не является способом обойти это ограничение.

Для советника предлагается минимальный набор чтения либо подготовленный пакет
материалов. Исключаются shell, edit/write, запускающие процессы инструменты,
делегация, изменяющие MCP и неконтролируемые hooks/plugins/skills. Проверки
охватывают дочерние процессы и доступ вне разрешённых материалов. Нативное
приватное хранение сессии отделяется от права менять проект. Одного обещания
модели «ничего не менять» недостаточно; при недоказанной изоляции роль не включается.

## Что означает сопоставимая поддержка с Codex

Равенство оценивается по пользовательским возможностям, а не по совпадению RPC.
Матрица пакета A различает проверенное, доступное с ограничениями, неизвестное
и неподдерживаемое. Неизвестная возможность не объявляется реализованной.

| Область | Целевой результат | Основная проверка |
| --- | --- | --- |
| Идентичность | Отдельный Claude runtime и ответная identity в Hub | Никакой подмены моделью Claude внутри другого runtime |
| Сессии | Start/resume точной сессии, сохранение после рестарта | Session ID, root binding, никаких молчаливых новых диалогов |
| Диалог | Ответы, прогресс, входящие материалы и результаты через Hub | Только разрешённый видимый текст, без hidden reasoning |
| Управление | Выбор доступных модели/effort, `/stop`, понятные ошибки | Возможности CLI, отсутствие зависания всей очереди |
| Полномочия | Разделение ведущего и советника, человеческие approvals | Ни роль, ни MCP, ни помощник не повышают права |
| Локальный интерфейс | `/local` и `/return` в ту же сессию | Завершение прежнего writer и сохранение ограничений роли |
| Подключение сессии | Выбор подходящей существующей Claude-сессии | Без запуска модели, чтения лишнего диалога и подмены root |
| Восстановление | Сохранённые результаты/частичные ответы и честная неопределённость | Сбой после вызова не вызывает автоматический повтор |
| Ресурсы | Подписочный режим, доступные context/limit сведения | Только пассивные источники; неизвестное остаётся неизвестным |

Same-turn steering, автоматическая ротация нескольких аккаунтов, точность
quota telemetry и возможности companion не обещаются как побочный эффект
`--resume`. Если официального эквивалента нет, в матрице остаётся явный разрыв.
Текстовый прототип не завершает цель сопоставимой поддержки. Любое сокращение
обязательного объёма относительно согласованной матрицы — отдельное решение
владельца, а не скрытая подмена готовности.

## Узкий цикл сотрудничества

1. Пользователь включает режим и выбирает ведущего. Для планирования задаётся
   ограничение на раунды обсуждения и доступные ресурсы.
2. Ведущий готовит план и конкретный вопрос советнику. Hub сохраняет поручение,
   исходную ревизию/снимок и разрешённые материалы.
3. Ведущий завершает текущий turn; советник выполняет следующий явный turn.
   На первом этапе они работают последовательно. Нельзя держать ведущего
   внутри занятого FIFO-слота, ожидая подзадачу из той же очереди.
4. Советник возвращает замечания с основаниями. Hub передаёт их ведущему
   только в рамках сохранённого поручения и разрешённого продолжения.
5. Ведущий принимает решение, меняет проект и запускает проверки. Review
   относится к точному снимку результата; позднейшие изменения делают его
   недостаточным для утверждения о новой версии.

Для первой версии предлагается один раунд review и одна реакция ведущего;
продолжение за пределами установленного лимита требует нового поручения.
Нужны устойчивая запись поручения/ответа/continuation и дедупликация, но не
универсальный event bus, внешний A2A или граф произвольной рекурсивной команды.
Боты общаются через Hub, а не через доставку Telegram bot-to-bot сообщений.

Смена ведущего применяется между завершёнными задачами: старые вызовы,
помощники и approvals должны завершиться или остаться явно заблокированными.
Права старой роли отзываются до выдачи новых. Старые queued targets не
переписываются, а Reply/mention не становятся способом получить право записи.

## Пакеты первого этапа

| Пакет | Работа и результат | Оценка сосредоточенной работы |
| --- | --- | --- |
| A — границы и основа | Проверить текущий baseline, подписочный путь, approvals, read-only и session capabilities; подготовить owning contracts и тестовую матрицу | 3–5 рабочих дней |
| B — Claude runtime | Адаптер и fake fixtures, start/resume, структурированный поток, очередь/outbox, ограничения оплаты, ошибки и stop | 7–12 дней |
| C — ведущий/советник | Обе расстановки ролей, ограниченные поручения, снапшоты, последовательное продолжение, запрет записи и обходов | 5–8 дней |
| D — доведение возможностей | Human approvals, local/return, session connect, результаты после сбоев, доступная пассивная telemetry | 7–12 дней |
| E — помощники и минимум учёта | Ограниченные read-only поручения ведущего, наблюдаемый расход, приёмка/доработка и причина | 3–5 дней |
| F — приёмка | Регрессии Codex и остальных providers, fault scenarios, отдельно разрешённые live-проверки и rollback | 3–5 дней |

Суммарный ориентир — 28–47 рабочих дней, примерно 6–10 инженерных недель.
Это предварительная оценка, не измеренная скорость этой команды и не обещание
календарного срока. Она включает интеграцию и проверку; генерация кода — лишь
часть работы. Неподдерживаемый subscription/approval/session интерфейс может
потребовать пересмотра решения, а не добавления произвольного числа дней.

Ранний ограниченный прототип советника возможен в первые 1–2 недели при
успешной проверке пути доступа. Полная приёмка не объявляется по этому показу.
Оценка уточняется после A и первого проверенного start/resume в B.
После A отдельно назвать подтверждённый путь, блокеры и пересчитанные интервалы
оставшихся пакетов. До этой точки 6–10 недель не являются обещанием даты выпуска.
Практическая точка входа —
[следующая сессия](NEXT_DEVELOPMENT_SESSION.md).
Live-авторизация, credentials, сервисы и deployment — отдельная задача по
существующей политике; этот документ не выполняет и не принимает её.

## Минимум учёта вместо скоринга

В первом выпуске достаточно связи задачи с исполнителем/model/effort, точным
результатом, наблюдаемыми временем/usage, решением «принято / доработать /
неизвестно» и короткой причиной. Часть данных уже существует в jobs; добавлять
только недостающую связь с результатом и приёмкой. Расход потомков сохранять
как наблюдаемый или неизвестный, без двойного счёта и выдуманной цены подписки.
Пользователь не обязан ставить оценку каждому turn.

Это диагностический журнал, без leaderboard, вероятности успеха, обязательного
заполнения rubric, ML-сервиса или дополнительного judge-вызова. Долговременная
[основа оценки и распределения](../product/EVALUATION_AND_ALLOCATION.md)
сохраняется, но её автоматизация не является критерием готовности этого выпуска.

## Проверки перед завершением

- Невызванный советник не расходует inference; каждый разрешённый раунд
  имеет ограничение, устойчивую identity и ровно одно продолжение.
- Советник обоих runtime не меняет проект через tools, shell, hooks, MCP,
  смену роли, локальный интерфейс или помощников.
- Два ведущих не получают один root; рестарт и неизвестный stop не освобождают
  право записи без доказательства, а смена роли не активирует старые jobs.
- Истёкшая подписка/квота не включает API или платное продолжение. Обычные
  status/monitor операции не вызывают модель.
- Review привязан к предъявленному результату; потеря доставки не запускает
  повторное выполнение. Обе расстановки Codex/Claude проходят одинаковые сценарии.
- Тесты начаты с отказов и сбоев. Публикация проходит canonical gate на точной
  чистой ревизии; deployment, Telegram/provider и local round trip доказаны
  отдельно, без смешения уровней evidence.

Пакеты не требуют переписывать Controller или state целиком. Перед добавлением
ответственности в крупный модуль выбирается небольшая проверяемая граница,
с сохранением одного владельца транзакции и существующей queue.

## Когда возвращаться к расширению

После периода обычного использования измерить полезность советов, количество
переделок и незапланированное время обслуживания Hub. Параллельную запись
рассматривать при повторяющейся очереди независимых изменений; автоматический
скоринг — когда ручной выбор систематически становится затруднением и накоплены
сопоставимые данные. Ни один из этих этапов не включается автоматически.
