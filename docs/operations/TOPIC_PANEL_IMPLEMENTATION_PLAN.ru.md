## 1. Результат для пользователя и границы задания

В каждой зарегистрированной проектной теме владелец может открыть одну актуальную панель Hub: обычное Telegram-сообщение с HTML-форматированием и inline-кнопками. Оно показывает наблюдаемое состояние работы, очередь, последнее подтверждённое событие, исполнителя и владельца управления. Hub редактирует сообщение вместо отправки потока статусов. Задачи, ответы агентов, файлы и обязательные уведомления продолжают идти обычными сообщениями.

Реализовать именно этот интерфейс в существующих production-группах. Не использовать Telegram Widgets, Mini Apps, сайт, тестовую среду Telegram, новые боты или отдельный веб-сервер. Для исходной версии поддержать только настроенный Hub bot с внешними queue/outbox. Неподдерживаемые режимы должны явно отказывать без запуска модели. Не переводить пользовательскую работу в личные чаты.

Этот документ — инструкция по реализации, а не новый нормативный контракт и не доказательство готовности. До изменения поведения исполнитель должен обновить owning requirements и обосновать решение в ADR. План не разрешает сам по себе установку, включение новой default-off функции, live-запросы, смену credentials или ответы на approvals. При публикации и дальнейшей эксплуатации действуют актуальные полномочия из [AGENTS.md](../../AGENTS.md).

В первую поставку входят обзор, просмотр очереди, подробности, обновление, поднятие панели вниз командой, необязательное закрепление и безопасная остановка темы. Следующий ограниченный этап добавляет вход в существующий выбор модели. Реализацию всего плана нельзя объявлять завершённой после одного рендера или первого этапа.

## 3. Пользовательское поведение

### Открытие, обновление и размещение

- `/panel` создаёт панель внизу текущей зарегистрированной темы. Если предыдущая панель существует, это явный запрос на замену, а не попытка отредактировать её и обещать, что она переместилась вниз. Telegram edit не меняет положение сообщения.
- Кнопка «Обновить» перечитывает состояние и обновляет ту же панель. «Обзор», «Очередь», «Подробнее», «Назад» меняют только представление. Общая панель имеет один общий экран; не обещать независимый экран каждому читателю.
- Повторная доставка того же `/panel` не создаёт вторую панель. Быстрая серия разных `/panel` во время незавершённой отправки объединяется в один pending request; ограничить создание одной заменой за 10 секунд на тему.
- После подтверждённой замены прежняя панель перестаёт быть актуальной. Убирать её кнопки и дописывать «Панель заменена» по возможности. Серверный отказ старым callbacks обязателен даже при неуспешном косметическом редактировании. Историю сообщений не удалять.
- Не создавать панель автоматически в каждой теме при старте сервиса. Первое открытие — явная команда владельца. После этого она обновляется, пока включена. `/panel off` отключает обновления и инвалидирует кнопки; `/panel` снова включает с новым экземпляром.
- `/panel pin` закрепляет только текущую подтверждённую панель без уведомления. Это необязательное действие; при отсутствии прав панель остаётся работоспособной. Не выдавать боту дополнительные права автоматически. Если включено закрепление, при замене закреплять новую и снимать только собственное старое закрепление, никогда чужие.
- Пока первичная отправка неизвестна, не закреплять и не активировать предполагаемое сообщение. При ambiguous pin не запускать автоматическую серию повторов; показать состояние при следующем запросе. Режим закрепления хранить отдельно от подтверждения конкретного pin.
- Добавить `/panel` только в меню зарегистрированных групп Hub и вход «Панель» в существующее `/menu`. Проверить синхронизацию старых и новых групп. `/panel off` и `/panel pin` объяснить в краткой справке, не добавляя отдельные команды в меню.

### Пример обзора

Пример вымышленный, не acceptance transcript. Текст формируется по evidence; строки без данных заменяются на честное unknown или опускаются.

```text
🟢 Выполняется задача
Claude · выбранная модель
Очередь: 2 задачи · удержано: 1
Последнее событие: получен промежуточный ответ · 14:32
Управление: Telegram
Состояние на 14:33

[ Очередь · 2 ] [ Подробнее ]
[ Обновить ]   [ Остановить тему ]
```

Ограничить обзор примерно 10 строками и 1500 видимыми символами; подробности — 3000 символами, очередь — 5 записей на странице. Это внутренние ограничения меньше Telegram maximum. Пагинация должна работать на кириллице, emoji и HTML entities без сломанной разметки. Все динамические значения экранировать. Цвет дополняет текст, никогда не заменяет его.

Не писать «Проверяет тесты», если есть только работающий процесс. Не генерировать заголовки и резюме моделью. По умолчанию использовать «Задача №N», provider и ссылку на исходное сообщение своей темы, когда такая ссылка допустима и доказана. Не вытаскивать полный prompt, tool args, терминал или native transcript ради красивого названия.

### Очередь и подробности

- Считать provider jobs, а не Telegram messages: несколько входов могут быть объединены в один job или использованы как correction. Подписать единицу «задачи». Pending input, ещё не ставший job, показывать отдельно, только если для него есть существующий надёжный источник.
- Показывать текущую работу, затем ожидающие в фактическом FIFO; held — отдельным числом/списком. Не включать завершённые задачи в очередь. Различать ожидание worker, другой темы на том же root, delivery и явного решения.
- Пагинация не должна пропускать или ошибочно дублировать задачи при изменении очереди: использовать bounded snapshot/cursor; устаревший cursor сбрасывать на начало с объяснением. Не хранить неограниченные копии очередей.
- В подробностях: observed state/time, исполнитель конкретной задачи, отдельно выбранный исполнитель для следующих задач, writer, доступная телеметрия, причина блокировки, доставка последнего результата. Satellite job не подписывать моделью active session.
- Кнопку «Управление очередью» из концептуального макета не реализовывать как новую систему управления. В этой задаче очередь только читается; нет reorder, удаления отдельных jobs, retry, release held или массового cancel за пределами существующего Stop.
- При проблеме доставки показывать «Результат сохранён; доставка не подтверждена». «Действия» — только переход к уже существующему точному warning/preview или объяснение, где он находится. Не вызывать `/delivery` от имени человека и не создавать recovery consent из кнопки панели.

## 4. Как вычислять состояние без выдуманных фактов

Хранить отдельно оси execution, delivery, writer, freshness и stop. Один общий enum «всё зелёное» недостаточен. Renderer выбирает главный заголовок, но не скрывает остальные существенные состояния.

| Наблюдение | Допустимая формулировка | Запрещённый вывод |
| --- | --- | --- |
| Queued без invocation | «В очереди», с известной причиной | «Агент работает» |
| Lease/подготовка, нет принятого turn | «Подготовка запуска» | «Задача принята моделью» |
| Доказанное принятое выполнение | «Выполняется» | Процент готовности, ETA, выдуманная стадия |
| Только owned Claude process | «Процесс запущен; последнее наблюдение…» | Native acceptance или гарантированная активность модели |
| Свежий exact-bound approval wait | «Нужно решение в существующем канале подтверждения» | Allow/Deny на панели или утверждение, что карточка доставлена без receipt |
| Stop intent без terminal proof | «Остановка запрошена» | «Остановлено» |
| Terminal interruption подтверждён | «Выполнение остановлено», отдельно состояние очереди | Удаление uncertainty или автоматическое продолжение held jobs |
| Result сохранён, final ещё ожидает | «Результат сохранён; ожидает доставки» | «Ответ доставлен» |
| Delivery unknown | «Доставка не подтверждена», отдельно блокирует ли она сейчас | «Ответ потерян», «можно повторить» |
| Final имеет положительный receipt | «Ответ отправлен в тему» | «Прочитан пользователем», «работа принята владельцем» |
| Writer local/terminal | «Управление в локальном терминале» | Автоматический `/return` или запуск второй сессии |
| Источник недоступен/устарел | «Нет свежих данных; состояние на…» | Idle, completed или healthy по отсутствию данных |

Приоритет заголовков: неизвестный исход/актуальный blocker → незавершённый stop → approval → local writer → execution/queue → последний завершённый результат/idle. Если несколько условий истинны, показать дополнительные строки; старое разрешённое неизвестное событие не объявлять нынешней блокировкой. Переиспользовать действующие predicates.

Время «Выполняется N мин» допустимо только от доказанного старта и называется длительностью наблюдаемого выполнения; queued age и leased age — другие значения. Без старта опустить длительность. Не обновлять сообщение раз в секунду ради часов. Время «Состояние на…» относится к snapshot; время последнего события — отдельное поле. Часовой пояс брать из поддержанного источника, иначе явно UTC, не из машины разработчика.

## 5. Архитектура минимальной реализации

Предлагаемые новые модули: `topic_panel_view.py` (DTO и pure render), `topic_panel_state.py` (bounded projection и lifecycle), `topic_panel_controller.py` (команды/callbacks), `topic_panel_sender.py` (send/edit/pin). Допустимы другие имена с той же границей ответственности. Не создавать универсальный UI framework, новый event bus, ORM, отдельную БД или daemon.

Поток: проверенный Telegram input → Controller → короткая SQLite-транзакция UI intent → существующий внешний sender → Telegram → короткая транзакция receipt. Периодическое обновление читает существующее состояние; provider workers не получают Telegram credentials и не вызывают renderer или sender.

- Снимок собирать в короткой согласованной read transaction, через facade. Не держать транзакцию во время HTTP, ожидания callback или polling. Не читать все jobs/history и не брать write-lock ради неизменившегося snapshot.
- На первом проходе использовать bounded polling внутри существующего sender. Достаточно одного обслуживания активной панели за 5 секунд на тему; не сканировать всю базу каждые 200 мс. Обход панелей — bounded round-robin. Idle панели проверять не чаще раза в минуту; explicit refresh может запрашивать свежий snapshot с учётом cooldown.
- При неизменном смысловом содержимом не делать edit; один timestamp не повод для отправки каждую проверку. Ограниченный heartbeat свежести допустим не чаще минуты. При недоступности данных сохранять прежнюю временную отметку.
- Panel send/edit обслуживать после обязательных результатов, stop/approval/control notices и существующих workflows. Не ломать fairness текущего sender. Если панель голодает, она остаётся устаревшим snapshot; нельзя снижать приоритет финальных ответов ради её свежести.
- Ошибка панели изолирована: она не меняет provider health, root ownership, queue admission или delivery holds. Диагностика содержит только безопасный код, без prompt, путей, токенов и сырого HTTP body.

### Данные панели и миграция

Спроектировать минимальные additive таблицы под существующий `HubState`; не фиксировать здесь будущий номер schema. Нужны следующие логические записи, допускается компактное объединение при сохранении инвариантов:

1. Текущая панель темы: numeric chat/thread, project/topic binding, bot identity, enabled, instance/generation, подтверждённый message ID или null, текущий экран, pin preference, desired/applied revision, content digest, checked/observed time, next due.
2. Операция доставки: ID, вид create/edit/retire/pin, immutable destination/payload revision, lease, send-start, deadline, попытка, outcome pending/confirmed/rejected/unknown, положительный receipt. Не путать неизвестную отправку панели с неизвестным результатом provider.
3. Управляющий ticket: opaque bounded key, допустимые configured owners, bot/chat/topic/message, panel instance, session generation, action, expiry, applicable work identity для Stop, consumed decision с точным actor. Общая карточка доступна текущим configured owners; при изменении их состава старые mutation tickets отзываются. Запись нужна до показа управляющей кнопки; message binding завершается только после точного send receipt.
4. Дедупликация команд и callback decisions. Повтор одного update или одного action ticket возвращает исходное решение, а не создаёт новый intent. Callback query ID сам по себе недостаточен: двойной tap создаёт разные query IDs.

Данные UI не становятся источником истины для jobs. Не копировать туда transcripts и токены, не изменять provider jobs из renderer. Unique current-instance constraint и compare-and-swap защищают конкурентные команды. Сохранять только bounded недавние версии/decisions; неизвестные attempted operations и их evidence не удалять обычным TTL. Исчерпание UI-бюджета отключает новые panel sends и объясняется через команду, не блокирует проекты.

Базовые технические границы зафиксировать в named constants и тестах: не более 20 due panels за один read pass, 5 записей очереди на страницу, один UI HTTP effect за sender cycle; TTL mutation ticket 15 минут. Перед истечением при активной работе обновить ticket в очередном допустимом edit; при паузе sender истёкшая кнопка предлагает «Обновить». UI cleanup не стирает последний consumed action и unknown evidence. Конкретный лимит сохраняемых исторических UI-операций обосновать и проверить на этапе 2; не оставлять неограниченный append-only поток на каждую секунду работы.

Миграция обязана проходить на populated fixture, создавать предусмотренный backup и откатывать DDL при ошибке. Старый runtime не считать совместимым с новой схемой по предположению. До deployment подготовить и проверить runtime rollback на сохраняемой схеме, без автоматического восстановления БД.

## 6. Доставка и замена панели

### Первое создание и явная замена

1. Авторизовать `/panel`, сохранить dedup и новый create intent. При замене атомарно отозвать старые управляющие tickets до начала новой отправки; сохранить старый message ID для косметического retirement.
2. Sender захватывает конкретную операцию и фиксирует send-start перед HTTP. Не держит SQLite lock во время сети. Новый message ID принимается только из валидного положительного результата Telegram, не из предположения или следующего update.
3. Receipt сохраняется для точной операции. Только после этого activate новый instance и его кнопки. Поздний receipt старой операции сохраняется как evidence, но не делает её current.
4. Ошибка до send с доказательством отсутствия эффекта или доказанный API reject допускают bounded retry; учитывать bot-wide `retry_after`. Timeout/обрыв после возможной отправки — unknown, без автоматического повторного create.
5. При unknown предыдущая карточка остаётся безопасно неуправляющей. Новый явный `/panel` может создать другой instance с сообщением о возможной лишней старой карточке; это новая просьба, не повтор неизвестной операции. Никогда не обещать физически одно сообщение при сетевой неопределённости; гарантировать не более одной действующей панели.

### Редактирование

- Точный target — bot/chat/message и panel instance, никаких поисков сообщения по тексту/названию темы. Привязку сверять перед отправкой и перед применением receipt.
- В один момент не больше одного edit на message. Coalesce ожидающие изменения до последнего snapshot; lease expiry не доказывает, что старый HTTP writer завершён. Поздний edit не должен откатить новое состояние или снова активировать старые кнопки.
- При ambiguous edit отметить отображение неподтверждённым, инвалидировать затронутые mutation tickets и не слать следующие edits в тот же message, пока отсутствует надёжное завершение старого запроса. Если это нельзя доказать существующим transport, восстановление — новый instance по `/panel`, без повторения действий пользователя.
- `message is not modified` считать безопасным достижением требуемого отображения только для exact-target/exact-payload edit с известным API reject; это не подтверждение выполнения Stop и не delivery receipt результата агента.
- Удалённое/недоступное сообщение и потеря прав означают, что панель недоступна. Не создавать автоматически замену при каждой ошибке. Следующая явная `/panel` предлагает восстановление; `/stop`, `/status` и обычные ответы остаются доступны.
- При restart восстанавливать confirmed mapping и pending UI intents, но attempted create/edit с неизвестным исходом не отправлять заново. Только UI state восстановлен — это не восстановление выполнявшейся задачи.

## 7. Callback безопасность и Stop

Для любого panel callback проверить точный configured owner, разрешённый numeric chat/thread, registered project, numeric Hub-bot author, message ID, current instance, action и ticket. Проверять серверное состояние, не доверять тексту кнопки, username, topic title, переданному пути или client timestamp. Callback payload не больше 64 UTF-8 bytes, без filesystem path и native session ID; opaque key не заменяет проверку actor/origin.

Read-only кнопки могут получать актуальный snapshot только своей темы. Старые панели отвечают «Панель устарела; откройте /panel», ничего не изменяют. Неизвестный action, malformed data, отсутствующая запись и отказ БД всегда остаются control-only: никогда не превращать их в prompt.

### Точное поведение остановки

- Название: «Остановить тему». Рядом кратко объяснить: прерывает текущую Hub-работу этой темы и отменяет допустимые ещё не начатые задачи; held work и другие темы не меняются. Не называть это остановкой всей системы или одного выбранного агента.
- Одно нажатие, без дополнительного confirmation dialog: Stop должен оставаться быстрым. При локальном writer не обещать остановку внешнего CLI; для unsupported режима кнопки нет и объясняется граница.
- Нельзя просто синтезировать `/stop` из panel message ID: один и тот же message обслуживает разные задачи, и dedup по message ID может применить старый Stop или поглотить новый.
- Сделать узкий общий transaction-level вход существующей stop-логики, если его ещё нет. В одной транзакции проверить current panel, owner ticket, expected work/session generation, затем записать consumed ticket, durable stop request и существующий notice. Не копировать SQL state machine в panel module и не делать nested independent transactions.
- У panel Stop должна быть отдельная collision-free durable command identity с привязкой к ticket. Не выдавать вычисленный hash за Telegram message ID и не использовать ID панели как ID пользовательского stop-сообщения. Existing message-based `/stop` dedup сохранить; способ связать оба origin с общей логикой описать и проверить до wiring.
- Stop ticket относится к показанной текущей работе; если эта работа закончилась и другая уже началась, нажатие отказывается с обновлением панели. Для queue-only состояния использовать стабильную идентичность начала очереди и актуальную session generation. Очередь, уже существующая при принятии действительного topic-wide Stop, обрабатывается существующей семантикой.
- Два разных callbacks одного Stop ticket дают один request и одно решение. Повтор не расширяет coverage на новые jobs. Два владельца не создают два эффекта из одного instance/action: serialize и повторно проверить consumed/current work.
- `answerCallbackQuery` означает только реакцию интерфейса. «Остановка запрошена» выводится после durable intent, «Остановлено» — только по existing terminal evidence. Ошибка отображения не отменяет сохранённый Stop и не запускает второй.
- `/stop` сохраняется как независимый аварийный путь и работает при отключённой/сломавшейся панели. Её callbacks не получают права подтверждать approvals, отпускать root locks, продолжать FIFO или сбрасывать неизвестность.

### Выбор модели отдельным этапом

Кнопка «Модель» открывает существующий cascaded selector в этой теме. Переиспользовать `ControllerCommandOrchestrator` и cached catalog; выбор не вызывает модель и не меняет уже принятый job. У selector должны сохраниться/появиться точные message/session/catalog guards и ограничения при busy/local/uncertain work. Нельзя считать existing `bind_controls` полной защитой для любой сессии. Если такой reuse требует отдельного исправления, завершить его как ограниченную prerequisite-задачу, а кнопку до готовности не показывать. Account switch, `/new`, `/return`, `/local` на панель в этом плане не переносить.

## 8. Последовательность реализации и проверяемые результаты

Каждый этап: сначала failing behavior test, затем минимальная реализация, затем focused checks. Не начинать следующий этап с красными проверками предыдущего. Отмечать завершённое и оставшееся; публикационные gates применяются перед PR/merge по актуальным правилам.

| Этап | Сделать | Критерий выхода |
| --- | --- | --- |
| 0. Уточнение contracts | Сверить актуальный main, создать ADR, обновить owning UX/control/delivery clauses; выбрать schema и ограниченный rollout | Нет противоречий с меню, stop scope, privacy, no-replay и sender ownership; исходная карта evidence готова |
| 1. Проекция | DTO, bounded consistent read, pure renderer overview/queue/details, safe labels | Все состояния из раздела 4 отражены; нет transport/provider вызовов, полных prompts и mutation SQL |
| 2. Lifecycle | Additive UI tables, dedup, mapping, generation, intents/receipts, version guards | Restart, rollback, concurrent `/panel`, late receipt и unknown create покрыты реальной temporary SQLite |
| 3. Controller и sender | `/panel`, off, refresh/navigation, send/edit, menu sync, rate limits, priority | Панель обновляется через fake Telegram; control input не становится задачей; mandatory delivery не блокируется |
| 4. Stop | Guarded common stop entry и одноразовый ticket; truthful pending/terminal UI | Старый или повторный Stop не действует на новую работу; topic scope и existing semantics сохранены |
| 5. Завершение UX | Pin/replace/retire, устаревание, модель через existing selector | Права pin необязательны; недоступность Telegram не создаёт цикл отправок; модель меняется без inference |
| 6. Приёмка и публикация | Regression, canonical/privacy/history, независимый review и hosted gates; обновить evidence | Точный reviewed SHA, пройденные gates; опубликованная готовность не названа installed acceptance |
| 7. Разрешённая активация | Подготовить feature flag/config, backup/rollback, canary и отключение | Отдельно разрешённый rollout; проверена реальная тема, сохранён recovery; owner имеет конкретный отчёт |

До активации default-off флаг в локальной конфигурации отключает создание/обновление/действия панели. Проверять его также на поздних callbacks. Без флага Hub всё равно перехватывает `/panel` до маршрутизации: создание отказывается, `/panel off` закрывает существующую панель (ревью Astra 2026-11-21). Не оставлять скрытый always-on polling, миграцию при read-only status или новые service units.
