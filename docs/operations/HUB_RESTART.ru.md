# Обновление Hub с самостоятельным сообщением о результате

Это порядок перезапуска служб с независимой доставкой результата, пригодный
для инструкций внешней инфраструктуры и её recovery-агента. Перезагрузка
компьютера требует отдельного плана для Codex app-server, описанного ниже.
Конкретные пути, ревизии, службы и квитанции хранятся в приватном handoff
установки; этот документ не подтверждает состояние какой-либо установки.

## Перед первым изменением

1. Прочитать приватный `NEXT_AGENT_HANDOFF.md` и актуальную квитанцию операции.
   Сверить их с systemd, процессами и файлами. Завершённый или уже потреблённый
   исполнитель не запускать повторно. При неизвестном исходе сначала установить
   фактические эффекты; recovery оформлять отдельной узкой операцией.
2. Подготовить чистый candidate, совместимый rollback, конфигурацию и точный
   перечень затрагиваемых служб. Обновить recovery-каталог и проверить capsule
   по [подготовке релиза](IMMUTABLE_RELEASES.md). Использовать проверенную
   процедуру; повторное source review требуется при изменении её логики,
   а привязку новой операции проверить отдельно. Не переустанавливать уже
   проверенный неизменяемый runtime без необходимости.
3. До остановки Hub запустить независимый одноразовый наблюдатель в отдельной
   user-службе systemd, вне worker/controller. Привязать его к новой операции,
   digest плана и точному числовому месту ответа из доверенного состояния.
   Проверить PID/cgroup, готовность и запас времени на ожидание, обновление
   и восстановление. Он не вызывает модель и не управляет службами.
4. Запустить отдельный исполнитель, который дождётся завершения инициирующего
   хода **и подтверждённой доставки его финального ответа**. Рабочий агент
   должен закончить ход, чтобы исполнитель мог безопасно перезапустить worker.
   Наблюдатель уже должен работать в этот момент.

## Окно обслуживания

5. Повторить проверки занятости, неопределённых исходов, controls, локальных
   клиентов, конфигурации и владения native endpoint. Закрыть приём новых задач,
   перепроверить свободное состояние перед остановкой потребителей. Занятый
   клиент не убивать автоматически. Новая задача вправе прервать обновление.
6. Создать SQLite-consistent backup и проверить целостность/схему; связать его
   с candidate, rollback и конфигурацией через `release-manifest create/verify`.
   Сохранять intent перед каждым эффектом и readback после него. Применить
   подготовленные файлы, выполнить `systemctl --user daemon-reload`.
7. Вернуть весь исходно активный набор: workers и sender, затем admission и
   provisioner, после них monitor one-shot и timer. Следовать фазовому
   восстановлению из [основного runbook](TLIVE_RELIABILITY.md), включая при
   отказе; не оставлять Hub выключенным после безопасно устранимой ошибки.
8. Проверить каждую обязательную службу: точный argv/загруженное определение,
   PID, свежий heartbeat, чистый Git SHA. Проверить новое успешное выполнение
   monitor и следующий запуск timer. `0/SUCCESS` у остановленной службы и
   один здоровый tlive не подтверждают возврат всего Hub.

## tlive и Codex app-server

- Это самостоятельные компоненты. В обычном обновлении Hub исключить их из
  restart-набора, если план не содержит отдельно разрешённой необходимости.
  Проверять прежние boot ID, PID/starttime, executable/hash и cgroup до и после.
- Для attach-only tlive проверить фактический режим и аутентифицированный
  read-only статус с тем же Codex-процессом. tlive не должен запускать,
  останавливать или подменять независимый app-server.
- Socket custody проверять через `unix_listener_custody.verify_listener`:
  слушающий endpoint, kernel inode и FD владельца. Accepted-соединения
  не являются дополнительными listeners. При подключении отдельно сверять
  `SO_PEERCRED`; pathname и наличие socket-файла недостаточны.
- После перезагрузки компьютера прежний процесс не существует. Если установка
  предусматривает ручной запуск app-server, выполнить новый проверенный план
  старта из [native runbook](TLIVE_RELIABILITY.md). Не включать autostart,
  не менять `Restart=no`, не использовать старую квитанцию и не запускать второй
  server. Сначала подтвердить native endpoint, затем attach-only tlive и Hub.
- Здоровье tlive и доставка настоящих карточек разрешения — разные проверки.
  Агент не нажимает Allow/Deny и не заменяет человека автоматическим решением.

## Сообщение владельцу и завершение

9. Независимый наблюдатель читает согласованную терминальную квитанцию и
   фактическое состояние служб. Сам отправляет успех, отказ или неизвестный
   исход через настроенного Hub bot в заранее привязанное место ответа,
   не ожидая следующего сообщения владельца. Успех требует завершённого плана
   и совпадения обязательных runtime-ревизий; liveness не отменяет отказ.
10. Перед отправкой сохранить единственный durable send intent, после — точный
    Telegram receipt с message/chat/thread ID. При неизвестном результате
    не повторять отправку вслепую. Потеря машины/наблюдателя или сети может
    помешать доставке; такую неопределённость сохранить. Обновить приватный
    handoff ссылкой на терминальную фазу, rollback и следующий шаг приёмки.

| Задача | Проверенный механизм |
| --- | --- |
| Независимый запуск и чтение служб | `systemd-run --user`, `systemctl --user show` |
| Backup и совместимость | SQLite backup API; `release-manifest create/verify` |
| Возврат исходного набора служб | `maintenance_window.MaintenanceWindow`, фазовая квитанция |
| Native socket и процесс | `unix_listener_custody.verify_listener`, process identity, `SO_PEERCRED` |
| Наблюдение и однократная доставка | Приватный deployment adapter: `launch.py`, `observe.py`, `notify.py` |
| Ожидание окончания своего хода | Приватный adapter: `arm_cutover.py`, `run_cutover.py` |

Приватные adapters не являются готовыми публичными CLI-командами. Их точные
проверенные версии и пути берутся из handoff; старый потреблённый запуск
не становится шаблоном для повторного исполнения.

## Согласования и границы ответственности

На одно обновление достаточно разрешения владельца на конкретный scope:
затрагиваемые компоненты, допустимый restart и rollback. Внутри уже разрешённого
scope выполнять подготовку, проверки, запуск наблюдателя и исполнителя без
повторных церемониальных вопросов. Новый approval нужен при расширении scope,
неустановленном прежнем эффекте или требовании sandbox; правила sandbox это
разрешение не отменяет. Allow/Deny команд модели остаются отдельными решениями.

Внешняя инфраструктура и Hermes используют этот документ как интерфейс к Hub.
Инфраструктура владеет синхронными обновлениями, хранением backup и host recovery;
Hub предоставляет свои точные application-артефакты, совместимость и квитанции.
Не восстанавливать старую БД поверх состоявшихся внешних эффектов. Установку,
runtime convergence и живую приёмку функционала отмечать раздельно.
